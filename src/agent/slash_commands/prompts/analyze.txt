任务目标：
1. 基于当前工作区的高价值文件、目录结构与关键入口，初始化一套"最小入口 + 主手册 + 专题文档"的 Agent 文档体系。
2. 将 `{target_doc_relative_path}` 作为后续开发主手册的总纲与索引；将适合独立阅读的细节按项目特征动态拆分到 `agents_docs/`，不要固定套模板，也不要为了拆分而拆分。
3. 显式识别并整理项目开发风格偏好与核心业务逻辑；当信息足够丰富时，优先沉淀为 `agents_docs/development_style.md` 和 `agents_docs/business_domain.md`。
4. 同步检查 `{agents_relative_path}` 是否已经明确列出 `{target_doc_relative_path}` 与 `agents_docs/` 的路径、用途和文档优先级；若未列出，必须一并补充到 `{agents_relative_path}` 中。
   执行写入 `{agents_relative_path}` 时使用路径 `{agents_path}`。
5. 完成后用简洁中文告诉用户你写入了哪些文件、覆盖了哪些重点，以及后续应如何维护这些文档。

执行流程：
1. 信息采集分两轮进行，两轮均完成后再开始写文档，不得仅凭第一轮结果落盘。

   第一轮（结构层）：
   - 读取 README.md、AGENTS.md、构建描述文件（pom.xml / package.json / pyproject.toml 等）、docs/ 目录。
   - 判断项目边界、模块关系、启动方式和已有规范。
   - 若存在 CHANGELOG.md 或 migrations/ 目录，一并采样，了解项目演进习惯和历史红线。

   第二轮（实现层）：不做全库扫描，沿以下路径定向采集：
   - 从对外入口（Controller / Router / Handler / API 定义）选取 2-3 个代表性的核心功能入口。
   - 沿调用链向下追踪直到数据持久层或外部依赖调用处，记录每一层实际承担的职责、数据在层间如何流转。
   - 重点标记"业务规则密集区"：条件分支多、注释多、改动频繁或命名带有明显业务含义的文件和方法。
   - 采样测试目录（优先集成测试），验证对业务规则的理解是否与测试用例一致；若存在不一致，以测试用例为准并在文档中注明。

   开发风格偏好采样：
   - 从项目中选取 2-3 个已完成的典型功能（优先选近期改动、业务复杂度中等的），沿完整调用链从入口到数据层逐层阅读，记录每一层实际承担的职责。
   - 对比多个功能的实现，归纳以下内容：
     - 新能力实际落在哪一层（不以命名判断，以代码实现判断）
     - 条件分支、校验逻辑、数据转换通常写在哪里
     - 哪些层是透传层，哪些层有实质逻辑
     - 是否存在绕过常规分层的快捷写法，以及它出现在什么场景
   - 风格偏好必须从现有代码实现中提取，不得以 README 或注释中的声称为准；若两者不一致，以代码为准并在文档中注明差异。
   - 采样完成后，将归纳结论沉淀为 agents_docs/development_style.md，正文以"在这个项目里，XXX 通常这样做"的陈述句写出，避免泛泛而论。

2. 按主题分段沉淀：将总纲写入 `{target_doc_relative_path}`，将具备独立阅读价值的专题知识写入 `agents_docs/`。

3. 统一整理：回看总纲、索引、交叉引用与文档优先级，消除重复、矛盾和只适合一次性总结的内容。

执行约束：
- 优先采用低成本、结构化、只读的方式获取信息，避免无边界地逐文件扫描整个仓库。
- 在整理正文前，必须先判断当前工作区属于单项目、聚合多模块，还是多个项目并存的工作区；如果存在多项目或多模块，必须先识别项目/模块边界，再继续整理手册。
- 对多项目或多模块场景，必须识别每个项目/模块的角色，例如服务、公共库、SDK、前端、脚本工程、基础设施或测试支撑模块，并明确哪些模块可独立启动，哪些模块只是被依赖的公共层。
- 对多项目或多模块场景，必须优先结合根目录与子目录下的 pom.xml、settings.gradle、build.gradle、package.json、pyproject.toml 等构建描述文件梳理依赖方向、聚合关系和构建边界，而不是只依据目录名猜测。
- 如果存在模块依赖链，必须在文档中明确写出依赖方向、公共能力推荐落点、变更影响面，以及通常的构建、启动、测试顺序。
- 这次生成是"第一版初始化"，首版应尽量稳定、可长期维护，避免快照式或一次性总结口吻。
- `{target_doc_relative_path}` 应聚焦稳定规则、关键边界、核心链路、扩展落点、阅读分流和测试要求，优先回答"怎么运行、怎么开发、关键代码改哪里、哪些模块不能乱改、需要遵守什么约束"。
- `agents_docs/` 只承载具备独立阅读价值的专题知识；优先考虑开发风格偏好、业务领域规则、模块边界、测试策略、扩展落点、运行或部署注意事项等主题。
- 开发风格偏好必须作为一等信息处理，至少识别：常见实现模式、模块拆分习惯、新能力通常落在哪一层、常见反模式与误改点、与现有代码风格一致的实现倾向。
- 业务领域知识必须作为一等信息处理，与架构信息同等优先级。当业务规则、核心实体、主要数据流信息足够支撑独立阅读时，必须生成 agents_docs/business_domain.md，内容包括：
  - 核心业务实体清单及关键字段含义
  - 主要业务规则（尤其是带条件分支的复杂规则，说明触发条件和预期结果）
  - 2-3 条核心数据流的完整路径描述
  - 容易被误改的业务逻辑及其原因
  该文档不写架构，只写"这个系统在业务上做什么、怎么做、哪里不能乱动"。
- 对高优先级规则、分层红线和常见误改点，应说明其核心意图；必要时补一句"为什么不能这样改"或"违反后可能造成什么问题"。
- 如果仓库较大或信息不足，不能等到全部分析完成后才第一次落盘；应按主题分段成稿，并在文档中明确说明"已覆盖范围""待补充区域"或"待确认项"，不得伪装为已全面完成。
- 如果多项目结构、依赖关系或启动方式识别不完整，必须在"风险点与待确认项"中明确说明未确认的模块、依赖方向或运行入口，禁止伪装成已经完整识别。
- 文档中需标注生成时间及所基于的代码版本或 commit（若可获取），便于后续判断文档时效性。对依赖具体实现、容易随代码变化而过时的内容，应在该段末尾注明"此部分依赖具体实现，代码变更后需同步核查"。
- 不得在文档中暴露 .env 内容、Token、密钥、凭证或其他敏感配置；涉及本地绝对路径、用户名等环境特定信息时，应避免原样记录，必要时做泛化或脱敏处理。
